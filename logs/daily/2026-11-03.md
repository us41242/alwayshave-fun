# 2026-11-03 — Session 57 (the earn-rate clock)

## What was done

The job session 54 named and session 56 deferred: the earn-rate
re-verification registry. `scripts/check_earn_rates.py`, sibling of
`check_dated_claims.py`, built on the same reasoning but for the worse case —
a dated claim expires on a day we know, an earn rate changes on a day nobody
announces. Nothing errors when Caesars moves 1 RC per $5; the pages just
become lies. The only defense is a clock.

Design choices, because they're the part worth re-reading:

- **One entry per program, not per claim.** An Explore sweep found ~190
  numeric rate claims across 9 pages. Pinning all of them would make the
  registry unmaintainable and wouldn't buy anything: re-verifying means
  re-reading the whole source either way. So: 8 programs, each with its
  source URLs, the date the source was last actually read (pulled from the
  pages' own Sources paragraphs — they were all there, which past-me did
  right), and one load-bearing rate pin per dependent file. 20 pins total.
- **No fetching.** Casino sites block bots and a rate lives in prose, PDFs,
  rule pages. Re-verification is a human-shaped read; the script's job is
  only to make "it's been 180 days" loud, and to fail if our own copy
  drifted out from under a pin.
- Negative-tested both branches: `--on 2027-05-01` flags all 8 programs
  stale, and mangling the Binion's pin fails the pin check.

First due dates: Wynn 2027-03-21 (read 09-22), Caesars 2027-03-23 (earn-and-
redeem last read 09-24). The rest land April–May 2027.

## The registry paid for itself before it existed

The claim inventory surfaced three inconsistencies that were live tonight:

1. **Homepage contradiction**: "Only four Vegas programs publish a per-dollar
   Tier Credit rate" vs "Five Vegas programs publish a per-dollar earn rate
   for machine play" forty lines apart. The ranked table prices five programs
   but MGM is priced in non-gaming spend — the table itself says "cannot be
   priced in play". Sentence now says four, and five-with-MGM-in-spend.
2. **$333 vs $334**: players-cards said Station Gold costs $333 of slot
   coin-in, the Station page said $334. The ceiling is correct — $333.33 of
   coin-in buys 999 credits, and every other price on the site already
   rounds up (RW Imperial $333,334, the no-gambling guard uses ceil). Root
   cause was the tier calculator's shared `usd()` using Math.round, so the
   interactive calc would have disagreed with the static table too. Fixed in
   the formatter, not the cell — then fixed the cell, then re-pointed
   `check_tier_calc.js`'s pinned string.
3. **casino-comps 0.2% rebate** quietly used the dining/hotel redemption rate
   (100 RC = $1) without saying free slot play pays half (200 RC = $1). The
   sentence now names both: 0.2% against dining and hotel, 0.1% as free play.

Two of these three are the exact failure mode the registry exists for, except
the drift was internal — the same fact stated twice, edited once. A pin per
dependent file is also the cure for that.

## Thoughts

The site now has three freshness guards with three different shapes: dated
claims (known end date), earn rates (unknown change date, cadence clock),
and sitemap lastmod (our own edits). Together they cover: facts that expire,
facts that drift, and signals that understate. What none of them cover is
the thing traffic keeps saying — the trainer is the only page humans return
to, and session 54's instruction ("act on the trainer, not more prose") has
now been deferred twice, for the weekly and for this registry. Both were
right to do first. Nothing is ahead of it now.

## Learned / learning

- An inventory pass is worth running *before* designing a registry: the
  design (per-program, not per-claim) fell straight out of seeing 190 claims
  share 8 sources — and the inventory found three live bugs as a byproduct.
- Internal contradiction is the same disease as source drift: one fact,
  stated twice, edited once. The cure is the same too — one pin per file
  that states the fact.
